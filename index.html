Data path · cost

What N copies cost our sensor traffic

Receive pathCopies (N)Share of one coreAdded latency per lidar frameMemory traffic
Proxy app behind the RM11~15%~14 ms~1.5 GB/s
App is its own RM5~7%~6 ms~0.7 GB/s
Fork0–1≤1.4%≤1.3 ms≤0.14 GB/s

At 10 Hz the frame budget is 100 ms, so 11 copies spend about a seventh of it moving bytes before anyone uses them. Each copy also evicts cache the consumer needed. Kernel copies aren't included.

The latency figures assume the copying thread is never time-sliced. On a loaded core it shares the CPU with other work, so the real added latency can be 2–3× higher: ~14 ms becomes 28–42 ms.

Back of the envelope
  • Lidar ~500 Mbps + radar ~50 Mbps ≈ 550 Mbps ≈ 69 MB/s
  • Lidar frame ≈ 6 MB at 10 Hz
  • Core: 2.5 GHz
  • A cache-cold copy runs at ~5 GB/s, or ~0.5 cycles per byte
  • One copy: 69 MB/s × 0.5 cycles/B ≈ 34 M cycles/s ≈ 1.4% of a core
  • One copy of one lidar frame: 6.25 MB ÷ 5 GB/s ≈ 1.25 ms
  • N copies: N × 1.4% of a core, and N × 1.25 ms
One lidar plus radar. Every additional large stream adds its share again. The 0.5 cycles/byte figure is deliberately middle-of-the-road for frames much larger than L2; a hot, in-cache copy can be several times faster, and a contended memory bus slower. Measure on your target.

Who owns the sockets, and why discovery has to live somewhere else

Data Ownership

  • Every byte crosses the RM: two kernel copies plus the userspace copies around them.
  • Single point of failure: if the OOM killer picks the RM, every SOME/IP flow on the ECU stops.
  • Wrong owner for socket settings: SO_RCVBUF, DSCP, receive thread affinity and back-pressure depend on the payload. The RM can't tune them per consumer.
We want the process that consumes the data to own the socket. In practice, every large-data app becomes its own routing manager.
vsomeip's shared-memory transport exists but has been fragile for us, so we don't use it. Subspace already covers local distribution.

✓ Multicast OFFER and FIND are copied to every bound socket, so they work.

✗ Unicast datagrams go to one socket only:

  • SubscribeEventgroup and its ACK
  • A unicast OFFER answering our FIND

These usually land on an RM that doesn't own the service.

SOME/IP-SD puts every unicast on the SD port, so you can't run several SD participants on one ECU address.
vsomeip binds the SD socket with SO_REUSEADDR (udp_server_endpoint_impl.cpp:92) so every RM can join the multicast group. Multicast is replicated to every socket; each unicast datagram is delivered to exactly one. Which one is a kernel detail (on Linux it's typically the most recently bound socket; SO_REUSEPORT would hash instead). Either way, it's not the RM that offers the service.

Discovery authority: one per ECU
  • Owns the SD port, and only the SD port
  • Speaks full SOME/IP-SD
  • Never touches payload bytes
Data-plane owners: many
  • Each app owns its own service ports
  • Tunes its own sockets

This separation supports our safety case: a component that isn't built to ASIL integrity never sits in the path of an ASIL flow.

Data Ownership · GM design

Lifecycle

Cold boot

No table on disk. The broker learns from the wire, writes the table, and publishes "table ready". Each RM loads and replays it.

Steady state

The SD port is silent. RMs notify prelearned subscribers directly and the broker is out of the data path.

Relearn (RID 0x0654)

A diagnostic request triggers a fresh learning session. RMs keep the last good table until the new one is on disk.

Broker crash

RMs keep running on their tables. The supervisor restarts the broker, which reloads from disk.

Crash isolation comes from the structure: the SD authority never owns a data port, and a data owner never owns the SD port.
The learning-table model is specific to GM's SDV SD extension. The general point, and what we'd like upstream, is that vsomeip's SD should be usable from a process that isn't a routing manager.

E2E: scatter-gather

Removing the copies the E2E API forces

E2E · today

The in-place protect contract

The app has to leave a hole for the E2E header:

SOME/IP hdr
hole
application payload

	// routing_manager_impl.cpp (3.6.1), send path
	its_buffer.assign(its_data + its_base,          // copy the body
	                  its_data + its_size);
	e2e_provider_->protect(key, its_buffer, inst);  // CRC in place
	its_buffer.insert(its_buffer.begin(),           // shift everything
	                  its_data, its_data + its_base);

	// receive path
	e2e_buffer its_buffer(_data + its_base,         // copy to check CRC
	                      _data + _size);
	e2e_provider_->check(key, its_buffer, inst, status);
  • Layers leak: every client needs to know header sizes and offsets, and a profile change means changing every app.
  • Send: 2 payload copies, one of them a full memmove.
  • Receive: 1 copy to check the CRC, then the app strips the header itself.
protect(e2e_buffer&) mutates one contiguous owning buffer, and the routing manager has to build that buffer. The copies come from the API shape, not from the CRC work.

E2E · proposal

The plugin returns pieces instead of mutating a buffer


	protect_result protect(buffer_view app_payload,
	                       instance_t instance);

	struct protect_result {
	    std::vector<byte_t> e2e_header;  // owned, small
	    buffer_view        app_payload; // span into the pin
	    std::vector<byte_t> e2e_footer;  // owned, usually empty
	    std::vector<byte_t> owned_app_payload; // Profile 01 only
	};

Routing composes a buffer_sequence without concatenating:

A nicer protect API alone isn't enough: if the result gets memcpy'd back into one train buffer, the copy is still there. The queue type and the socket call had to change together.

shared_ptr owns, views borrow

An API style that removes the remaining copies

Ownership

One buffer, many views, recycled when the last reference drops

shared_ptr<message_buffer_t> · use_count = 3
hdr
E2E
payload bytes
⇠
handler's shared_ptr<message>payload_impl view
forward to a local subscriberbuffer_sequence segment

message_buffer_pooldeleter returns the buffer to the pool when use_count reaches 0
  • Ownership is a type: holding a shared_ptr keeps the bytes alive, and a view never outlives its pin.
  • No stage copies "to be safe". The lifetime question is answered by the type system.
  • Bounded memory: a fixed-depth LIFO pool (default 8). A stalled remote TCP consumer drops frames instead of growing the heap.

Ownership · receive

Receive: the socket buffer is the message


	struct owned_buffer_slice {
	    message_buffer_ptr_t buffer;  // shared_ptr<vector<byte_t>>
	    std::size_t offset{0};
	    std::size_t length{0};        // explicit, never "0 = all"
	};

	// routing_host
	void on_message(owned_buffer_slice frame, ...);

	// application: the public API is unchanged
	app->register_message_handler(s, i, m,
	    [](const std::shared_ptr<message>& msg) {
	        auto p = msg->get_payload(); // a view of the pinned frame
	        keep_for_later(p);           // pins it; drop it to recycle
	    });
  • UDP: the datagram's shared_ptr is passed on as is
  • TCP: a full window is moved into a pool lease; otherwise it's copied out once
  • Local IPC: the command is sliced in place, with framing tags skipped
  • Proxy: the SOME/IP region is pinned; no deserializer::set_data
  • SD still takes const byte_t*, only for the duration of the call

Threads: strands, not mutexes

Using asio the way it was designed

Threads · today

A lot of locks

163mutex members (3.6.1)
~830lock sites
7recursive mutexes
30"deadlock" fixes in CHANGES, across 16 releases
  • client_endpoint_impl has a strand and four mutexes, one of them recursive
  • Server endpoints have no strand: mutex_, clients_mutex_, and a per-connection socket_mutex_
  • get_serializer() blocks on a condition variable when the pool is empty. The pool exists because of an earlier deadlock fix ("Use set of serializers to avoid deadlock situation").
Counts are for vsomeip 3.6.1 implementation/ (rg over *.hpp for mutex members and *.cpp for lock_guard, unique_lock, scoped_lock and shared_lock). 3.7.6 is at 135 members and 5 recursive mutexes, so it's moving in the right direction. The deadlock entries appear from v3.0.0 through v3.7.1.

Threads · today

A strand and a mutex guarding the same state


	// client_endpoint_impl.cpp: user thread
	bool client_endpoint_impl::send(const uint8_t* _data, uint32_t _size) {
	    std::scoped_lock its_lock(mutex_);                   // recursive_mutex
	    ...
	    train_->buffer_->insert(train_->buffer_->end(), _data, _data + _size);
	    ...
	    queue_.emplace_back(train_->buffer_, 0);
	    if (!is_sending_) {
	        is_sending_ = true;
	        boost::asio::dispatch(strand_, [..] { send_queued(entry); });
	    }
	}
	// asio completion handler
	void client_endpoint_impl::send_cbk(error_code const& _error, size_t _bytes, ...) {
	    std::scoped_lock its_lock(mutex_);                   // same lock again
	    queue_size_ -= queue_.front().first->size();
	    queue_.pop_front();
	    ...
	}

queue_, train_ and is_sending_ are per-connection state touched from both the user thread and asio's completion handler. That is exactly what a strand is for.

Threads · how strands work

A strand is a queue, not a lock

io thread 1
running A·h1
io thread 2
running B·h1
io thread 3
running C·h2
io thread 4
idle, or running another strand
session A strandh1h2h3← post()
session B strandh1h2
session C strandh2(h1 done)
  • Handlers on one strand never run concurrently, and they run in the order they were posted
  • Different strands run in parallel across the whole io_context thread pool
  • No thread ever waits. A busy strand just queues work, so there's nothing to deadlock on
  • post always queues. dispatch runs inline when already on the strand. bind_executor puts completion handlers and timers on the strand.

Threads · proposal

One strand per session; its state is touched only on that strand


	void session::send(buffer_sequence_ptr seq) {             // any thread
	    boost::asio::post(strand_,
	        [self = shared_from_this(), seq = std::move(seq)]() mutable {
	            self->queue_.push_back(std::move(seq));       // on strand_: no lock
	            if (!self->writing_) self->write_next();
	        });
	}

	void session::write_next() {                              // on strand_
	    writing_ = true;
	    boost::asio::async_write(socket_, queue_.front()->buffers(),
	        boost::asio::bind_executor(strand_,
	            [self = shared_from_this()](error_code ec, std::size_t) {
	                self->queue_.pop_front();                 // on strand_: no lock
	                if (ec || self->queue_.empty()) { self->writing_ = false; return; }
	                self->write_next();
	            }));
	}

The queue, the train, the socket, the dispatch timer and the connect state all belong to the session's strand. That removes mutex_, socket_mutex_, and both timer mutexes from each endpoint.

Threads · proposal

What still needs care

ConcernApproach
send() returns bool right away (queue limit)Check an atomic byte counter up front, then post. Report failures later through the completion handler.
Shared tables: routing info, subscriptions, offersOwn them on one routing strand, or publish read-mostly tables as immutable snapshots behind an atomic shared_ptr
User handlersKeep dispatching them on dispatcher threads, never on a session strand, so user code can't stall I/O
Blocking get_serializer()Mostly goes away: with copy elision, non-SD sends don't serialize the full frame
MigrationEndpoint by endpoint, TSan-gated. Client endpoints already have the strand, so they're the natural first step.
This is the one proposal that isn't implemented in the fork yet. We'd like to agree on the approach with the maintainers first.
