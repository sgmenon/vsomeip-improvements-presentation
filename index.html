The ADAS Use Case

Where SOME/IP sits in GM's ADAS compute

Use case

A vehicle with a split personality

HPC side: ADAS compute
  • A few large HPC SoCs (eg. running Linux and QNX)
  • Huge payloads: lidar, radar, camera, model feature maps
  • Workloads span SoCs over PCIe
  • Data-oriented design: We use Subspace for Pub/Sub and RPC over:
    • Primarily: Lock free shared memory
    • PCIe

MCU side: safety-critical controllers
  • Many small boards, mostly Classic AUTOSAR
  • Interfaces defined in ARXML

We chose the best middleware for the HPC side and the "bridge" specific Subspace Channels to SOME/IP efficiently at the boundary.

Data path · cost

What N copies cost our sensor traffic

Receive pathCopies (N)Share of one coreAdded latency per lidar frameMemory traffic
Proxy app behind the RM11~15%~14 ms~1.5 GB/s
App is its own RM5~7%~6 ms~0.7 GB/s

At 10 Hz the frame budget is 100 ms, so 11 copies spend about a seventh of it moving bytes before anyone uses them. Each copy also evicts cache the consumer needed. Kernel copies aren't included.

The latency figures assume the copying thread is never time-sliced. On a loaded core it shares the CPU with other work, so the real added latency can be 2–3× higher: ~14 ms becomes 28–42 ms.

Back of the envelope
  • Lidar ~500 Mbps + radar ~50 Mbps ≈ 550 Mbps ≈ 69 MB/s
  • Lidar frame ≈ 6 MB at 10 Hz
  • Core: 2.5 GHz
  • A cache-cold copy runs at ~5 GB/s, or ~0.5 cycles per byte
  • One copy: 69 MB/s × 0.5 cycles/B ≈ 34 M cycles/s ≈ 1.4% of a core
  • One copy of one lidar frame: 6.25 MB ÷ 5 GB/s ≈ 1.25 ms
  • N copies: N × 1.4% of a core, and N × 1.25 ms
One lidar plus radar. Every additional large stream adds its share again. The 0.5 cycles/byte figure is deliberately middle-of-the-road for frames much larger than L2; a hot, in-cache copy can be several times faster, and a contended memory bus slower. Measure on your target.

Who owns the sockets, and why discovery has to live somewhere else

  • Every byte crosses the RM: two kernel copies plus the userspace copies around them.
  • Single point of failure: if the OOM killer picks the RM, every SOME/IP flow on the ECU stops.
  • Wrong owner for socket settings: SO_RCVBUF, DSCP, receive thread affinity and back-pressure depend on the payload. The RM can't tune them per consumer.
We want the process that consumes the data to own the socket. In practice, every large-data app becomes its own routing manager.
vsomeip3 has no shared-memory transport: local traffic between apps and the routing manager goes over Unix domain sockets (or local TCP). Subspace already covers local distribution.

Data Ownership

Can we just have multiple routing managers on the SoC?

Not really It breaks service discovery
:30490 It's common in automotive to do SD on UDP port 30490, so every routing manager would bind the same port

Data Ownership

How several routing managers break service discovery

✓ Multicast OFFER and FIND are copied to every bound socket, so they work.

✗ Unicast datagrams go to one socket only:

  • SubscribeEventgroup and its ACK
  • A unicast OFFER answering our FIND

These usually land on an RM that doesn't own the service.

At least Service Discovery needs to be done by a single process.
This is just how SO_REUSEADDR works in POSIX sockets.
vsomeip binds the SD socket with SO_REUSEADDR (udp_server_endpoint_impl.cpp:92) so every RM can join the multicast group. Multicast is replicated to every socket; each unicast datagram is delivered to exactly one. Which one is a kernel detail (on Linux it's typically the most recently bound socket; SO_REUSEPORT would hash instead). Either way, it's not the RM that offers the service.

Data Ownership

The Solution

Separate discovery and socket ownership
Discovery authority: one per ECU
  • Owns the SD port, and only the SD port
  • Speaks full SOME/IP-SD
  • Never touches payload bytes
Data-plane owners: many
  • Each app owns its own service ports
  • Tunes its own sockets
  • Never binds the SD port
This also provides crash isolation (one of our safety requirements)
If this crashes… Single RM Split design
Single routing manager / SD authority All SOME/IP on the ECU stops Existing flows continue; only new discovery is paused
Large-data Client Application Flow stops; but UDP socket in RM is open Flows stop; socket is closed
This separation adds efficiency and safety.

Data Ownership · GM design

Active and passive SD plugins

  • Active plugin (in the SD broker): owns the SD port and speaks SOME/IP-SD on behalf of every app on the device.
  • Passive plugin (in each app's RM): receives socket updates from the active plugin and applies them. Events flow straight from the app's ports to remote subscribers.
The broker isn't a vsomeip application: it has no routing manager, no local IPC, and no service ports. All it needs from vsomeip is service_discovery_impl plus some implementation of service_discovery_host.

Data Ownership · GM design

Lifecycle

Discovery

The broker runs SOME/IP-SD. As offers and subscriptions arrive, the active plugin sends socket updates to the passive plugins.

Steady state

Each RM transfers Events and Method data to Subspace (recall it is 0 copy) from its own ports.

Broker crash

RMs keep their sockets and existing flows. The supervisor restarts the broker, and updates resume.

How the active plugin and the passive plugins exchange updates is GM-specific. The general point, and what we'd like upstream, is that vsomeip's SD should be usable from a process that isn't a routing manager.

Data Ownership · upstream ask #1

Standalone service discovery

The SD app could have been a RM with protocol=external service, but we didn't do that.

  • With this design, the standalone SD can be made using only vsomeip3-sd and some custom asio code
  • We did this by fully decoupling vsomeip3.so from vsomeip3-sd.so
  • Far simpler binary

E2E · today

The in-place protect contract

Today application code has to allocate a bufffer and leave a hole for the E2E header:

  • Send: 2 payload copies, one of them a full memmove.
  • Receive: 1 copy to check the CRC, then the app strips the header itself.
Fewer copies and fully contain E2E knowledge in the plugin.
protect(e2e_buffer&) mutates one contiguous owning buffer, and the routing manager has to build that buffer. The copies come from the API shape, not from the CRC work.

  • Ownership is a type: holding a shared_ptr keeps the bytes alive, and a view never outlives its pin.
  • No stage copies "to be safe". The lifetime question is answered by the type system.
  • Bounded memory on streams: TCP and local (UDS / local TCP) endpoints receive into a fixed-depth LIFO pool, 8 buffers by default, one pool per connection. When it runs dry, remote TCP drops the frame instead of growing the heap; local IPC allocates, so commands are never lost. UDP passes the datagram's own shared_ptr through, with no pool.

Threads: strands, not mutexes

Using asio the way it was designed

Threads · today

A lot of locks

163mutex members (3.6.1)
~830lock sites
7recursive mutexes
30"deadlock" fixes in CHANGES, across 16 releases
  • Multithreading is hard, I get it. And the T-San can only help that much.
  • client_endpoint_impl has a strand and four mutexes, one of them recursive
  • Server endpoints have no strand: mutex_, clients_mutex_, and a per-connection socket_mutex_
  • get_serializer() blocks on a condition variable when the pool is empty. The pool exists because of an earlier deadlock fix ("Use set of serializers to avoid deadlock situation").
Counts are for vsomeip 3.6.1 implementation/ (rg over *.hpp for mutex members and *.cpp for lock_guard, unique_lock, scoped_lock and shared_lock). 3.7.6 is at 135 members and 5 recursive mutexes, so it's moving in the right direction. The deadlock entries appear from v3.0.0 through v3.7.1.

Threads · how strands work

A strand is a single tasking queue
(so data access in the same strand doesn't need a lock)

Using SockerA·h1

Using SocketB·h1

Using SocketC·h2

session C strandh2(h1 done)
  • Handlers on one strand never run concurrently, and they run in the order they were posted
  • Different strands run in parallel across the whole io_context thread pool
  • No thread ever waits. A busy strand just queues work, so there's nothing to deadlock on
  • post always queues. dispatch runs inline when already on the strand. bind_executor puts completion handlers and timers on the strand.

	    socket_->async_write(boost::asio::buffer(*_entry.first), ...,
	        strand_.wrap([..](auto ec, auto n) { send_cbk(ec, n, buffer); }));
	}
	void client_endpoint_impl::send_cbk(error_code const& _error, size_t, ...) {  // on strand_
	    std::lock_guard its_lock(mutex_);                        // lock 1 again (If we used strand_ with async_write we didn't need it)
	    queue_size_ -= queue_.front().first->size();
	    queue_.pop_front();
	    if (queue_.empty()) is_sending_ = false;
	    else send_queued(get_front());
	}

Everything after send() already runs on strand_, yet each step still takes a lock. UDP is worse: its completion handler isn't on the strand at all, and send_queued sleeps for the SOME/IP-TP separation time while holding socket_mutex_, blocking an io thread.

vsomeip 3.6.1, TCP client: client_endpoint_impl.cpp:319 dispatches send_queued onto strand_; tcp_client_endpoint_impl.cpp:327-363 takes socket_mutex_ and wraps the async_write completion with strand_.wrap; client_endpoint_impl.cpp:514 send_cbk takes the recursive mutex_ again and calls send_queued for the next entry. UDP client: udp_client_endpoint_impl.cpp:199-229 holds last_sent_mutex_ and socket_mutex_, calls std::this_thread::sleep_for for the separation time, and binds send_cbk with plain std::bind, so the completion isn't on the strand.

The same code on the strand


	bool client_endpoint_impl::send(buffer_sequence_ptr_t _seq) {               // any thread
	    boost::asio::post(strand_, [this, self = shared_from_this(), seq = std::move(_seq)] {
	        train_->sequence_->append_sequence(*seq);            // on strand_: no lock
	        queue_.emplace_back(train_->sequence_, 0);
	        if (!is_sending_) {
	            is_sending_ = true;
	            send_queued(queue_.front());                     // already on strand_
	        }
	    });
	    return true;
	}
	void tcp_client_endpoint_impl::send_queued(entry_t& _entry) {             // on strand_
	    socket_->async_write(_entry.first->buffers(), ...,       // no socket_mutex_
	        boost::asio::bind_executor(strand_, [..](auto ec, auto n) { send_cbk(ec, n, buffer); }));
	}
	void client_endpoint_impl::send_cbk(error_code const& _error, size_t, ...) {  // on strand_
	    queue_size_ -= queue_.front().first->size();             // no lock
	    queue_.pop_front();
	    if (queue_.empty()) is_sending_ = false;
	    else send_queued(queue_.front());
	}

Same state, same order. The queue, the train, the socket, the dispatch timer and the connect state all belong to the connection's strand, which removes mutex_, socket_mutex_ and both timer mutexes from each endpoint. For UDP the separation time becomes a steady_timer on the strand instead of sleep_for.

This is the 3.6.1 function rewritten, not code from the fork; the strand work isn't implemented yet. Today send() returns false synchronously when the queue limit is hit. On a strand that decision happens later, so either keep an atomic estimate of queue_size_ for the fast check or report the drop through the send completion handler from the send-copy-elision change.

Threads · proposal

Work in progress: stay tuned

Strands per connection is proposal that isn't implemented in the fork yet. It touches a lot and we'd like to agree on the approach with the maintainers first.
Open questions, if asked: send() returns before the bytes are queued: the caller hands over an owned buffer (section 5). send() returns bool for the queue limit: check an atomic byte counter up front, then post; report failures later through the completion handler. Shared tables (routing info, subscriptions, offers): own them on one routing strand, or publish read-mostly tables as immutable snapshots behind an atomic shared_ptr. User handlers: keep them on dispatcher threads, never on a connection strand, so user code can't stall I/O. Blocking get_serializer(): mostly goes away, since non-SD sends no longer serialize the full frame. Migration: endpoint by endpoint, gated on TSan. Client endpoints already have a strand, so they're the natural first step.
